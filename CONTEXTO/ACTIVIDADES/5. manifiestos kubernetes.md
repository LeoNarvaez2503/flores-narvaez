# Actividad 5: Creación de Manifiestos YAML para Kubernetes (/k8s)

## 1. Descripción y Objetivo
Crear una carpeta unificada `/k8s` en la raíz del proyecto que contenga todos los manifiestos YAML declarativos para orquestar la infraestructura básica (Bases de datos, RabbitMQ) y los microservicios de la aplicación en un clúster de Kubernetes (Minikube / Kind). 

**Regla de Oro:** El evaluador ejecutará `kubectl apply -f k8s/`. Todos los recursos deben cargarse en el orden correcto y sin fallos.

---

## 2. Estructura de Archivos en `/k8s`

```text
/k8s
├── 01-configmaps-secrets.yaml
├── 02-pvc.yaml
├── 03-rabbitmq.yaml
├── 04-databases.yaml
├── 05-backend-deployment.yaml
├── 06-audit-deployment.yaml
├── 07-dashboard-deployment.yaml
└── 08-ingress.yaml
```

---

## 3. Especificación Detallada de los Recursos

### 3.1. ConfigMaps y Secrets (`01-configmaps-secrets.yaml`)
- **Secrets:** Almacenar credenciales sensibles en Base64:
  - Credenciales de PostgreSQL (`POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB`).
  - Credenciales de RabbitMQ (`RABBITMQ_DEFAULT_USER`, `RABBITMQ_DEFAULT_PASS`).
  - Secret de firma JWT.
- **ConfigMaps:** Variables de configuración no sensibles:
  - URLs de conexión usando DNS interno de K8s:
    - `RABBITMQ_HOST`: `rabbitmq-service.default.svc.cluster.local`
    - `DATABASE_HOST`: `postgres-service.default.svc.cluster.local`

### 3.2. Persistencia PVC (`02-pvc.yaml`)
- `PersistentVolumeClaim` para la base de datos del backend principal.
- `PersistentVolumeClaim` para la base de datos del microservicio de auditoría.
- `PersistentVolumeClaim` para los datos persistentes de RabbitMQ.

### 3.3. RabbitMQ (`03-rabbitmq.yaml`)
- `Deployment` o `StatefulSet` de `rabbitmq:3-management-alpine`.
- `Service` de tipo `ClusterIP` exponiendo puertos `5672` (AMQP) y `15672` (Management UI).

### 3.4. Backend Deployment & Service (`05-backend-deployment.yaml`)
- `Deployment` con réplicas configurables (mínimo 1).
- Inyección de variables de entorno desde Secrets y ConfigMaps.
- **Health Checks Obligatorios:**
  ```yaml
  livenessProbe:
    httpGet:
      path: /api/health
      port: 3000
    initialDelaySeconds: 15
    periodSeconds: 10
  readinessProbe:
    httpGet:
      path: /api/health
      port: 3000
    initialDelaySeconds: 5
    periodSeconds: 5
  ```
- `Service` de tipo `ClusterIP` exponiendo el puerto `3000`.

### 3.5. Microservicio de Auditoría (`06-audit-deployment.yaml`)
- **Escalabilidad:** `replicas: 2` (requisito de evaluación para verificar consumo de cola competitiva sin duplicar mensajes).
- Inyección de variables de entorno (RabbitMQ URL, Audit DB URL).
- `livenessProbe` y `readinessProbe` definidos en el puerto del microservicio (`3001`).
- `Service` de tipo `ClusterIP` exponiendo el puerto `3001`.

### 3.6. Dashboard Web (`07-dashboard-deployment.yaml`)
- `Deployment` de Nginx / Node (`replicas: 1`).
- `livenessProbe` y `readinessProbe` hacia `/` en el puerto `80`.
- `Service` de tipo `ClusterIP` exponiendo el puerto `80`.

---

## 4. Criterios de Aceptación de la Actividad
- [ ] La carpeta `/k8s` contiene todos los archivos YAML necesarios.
- [ ] Todos los Deployments incluyen `readinessProbe` y `livenessProbe`.
- [ ] La comunicación entre servicios utiliza la resolución DNS interna de Kubernetes.
- [ ] El microservicio de auditoría está configurado con 2 réplicas.
- [ ] Todos los recursos se pueden aplicar secuencialmente o mediante `kubectl apply -f k8s/`.

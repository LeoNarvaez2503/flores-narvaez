# Actividad 7: Despliegue en Kubernetes, Pruebas de Escalabilidad y Verificación

## 1. Descripción y Objetivo
Realizar el despliegue integrado del sistema mediante un único comando `kubectl apply -f k8s/` y ejecutar la batería de pruebas de validación requeridas en la rúbrica de evaluación (estado de pods, health checks, Ingress, resiliencia y escalabilidad horizontal del microservicio de auditoría a 2 réplicas sin duplicación de mensajes).

---

## 2. Flujo de Despliegue Paso a Paso

### Paso 1: Inicialización del Clúster y Entorno Docker
```bash
# 1. Iniciar Minikube
minikube start --driver=docker

# 2. Habilitar Ingress Controller
minikube addons enable ingress

# 3. Configurar la consola para construir imágenes dentro del demonio de Docker de Minikube (opcional si se usan imágenes locales)
eval $(minikube -u docker-env)  # En Linux/macOS
# minikube docker-env | Invoke-Expression # En Windows PowerShell
```

### Paso 2: Construcción de Imágenes Docker
```bash
docker build -t cavalocal-backend:latest ./backend
docker build -t cavalocal-audit:latest ./audit-service
docker build -t cavalocal-dashboard:latest ./web
```

### Paso 3: Despliegue Unificado con `kubectl apply`
Ejecutar desde la raíz del proyecto:
```bash
kubectl apply -f k8s/
```

---

## 3. Batería de Pruebas de Verificación y Criterios de Aceptación

### Prueba 1: Verificación de Estado y Health Checks de Pods
```bash
kubectl get pods -w
```
- **Resultado Esperado:** Todos los pods (`backend`, `audit-microservice`, `dashboard`, `rabbitmq`, `postgres`) deben estar en estado `Running` y con los probes en estado `READY (1/1)` o `(2/2)` en un tiempo prudencial.

### Prueba 2: Verificación de Enrutamiento Ingress
Probar acceso vía navegador o `curl`:
- `curl -I http://conjunta3p.espe.edu.ec/dashboard` -> Debe retornar `200 OK`.
- `curl http://conjunta3p.espe.edu.ec/api/audit` -> Debe retornar JSON con la lista paginada de auditorías.

### Prueba 3: Prueba de Escalabilidad Horizontal (2 Réplicas de Auditoría)
Verificar que el microservicio de auditoría pueda escalar sin generar duplicados en el consumo de RabbitMQ:
```bash
# Escalar a 2 réplicas
kubectl scale deployment audit-deployment --replicas=2

# Verificar que existan 2 pods corriendo
kubectl get pods -l app=audit-microservice
```
- **Validación de Cola Competitiva:** Enviar 10 peticiones POST/PUT/DELETE al backend -> Verificar que cada mensaje de auditoría sea procesado por exactamente **una** de las réplicas (RabbitMQ round-robin / cola competitiva) y que en la base de datos de auditoría existan exactamente 10 registros (ningún registro duplicado).

### Prueba 4: Prueba Integrada End-to-End (E2E)
1. Abrir el dashboard en `http://conjunta3p.espe.edu.ec/dashboard`.
2. Realizar una acción de escritura en el backend principal (ej. Crear o actualizar un vino vía POST/PUT).
3. Confirmar que en el dashboard SSE aparezca el nuevo evento de auditoría en **≤ 2 segundos**.
4. Hacer clic en la fila del evento y verificar que el JSON muestre las propiedades `entity`, `action`, `userId`, `timestamp` y `data` (`before`/`after`).

---

## 4. Criterios de Aceptación de la Actividad
- [ ] `kubectl apply -f k8s/` ejecuta y despliega todos los recursos sin errores sintácticos ni dependencias faltantes.
- [ ] Todos los pods alcanzan el estado `Running` con liveness y readiness probes pasando.
- [ ] El microservicio escala a 2 réplicas sin duplicar mensajes en la base de datos de auditoría.
- [ ] La latencia desde la acción en el backend hasta el reflejo en el Dashboard SSE es ≤ 2 segundos.
